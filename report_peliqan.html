Black-Box Security Assessment · Staging

Peliqan Platform — Red Team Findings Report

Targets: api / app / admin .staging.peliqan.eu Footholds: unauthenticated API · shared DEMO session Date: 2026-08-24/25 Status: Final (staging, no prod pivot)

Executive Summary

The assessment verified the platform's two primary defences — the demo read-only write-gate and object-level (owner-scope) authorization — and both held under targeted mutation and IDOR testing. The edge better-auth path blocklist was not bypassable with the available normalizer-variant set. No privilege escalation from the DEMO session to write or to another tenant's data was found.

The strongest issues are in the unauthenticated attack surface: client-controllable rate limits (X-Forwarded-For), open self-registration, an unauthenticated impersonation-token exchange whose token travels in the URL with no origin check, a Set-Cookie side channel on the demo-session mint, and spec/key disclosure (OpenAPI schema, JWKS, service health). One availability bug was induced in staging: a document uploaded with a filename over 255 characters wedges the owner's (and the admin's) document list into a persistent 400 (F9).

Detailed Findings

F1 Per-IP rate limits reset via X-Forwarded-For spoofing HIGH

Summary. Every per-IP rate limit on staging (sign-in 3/60s, sign-up 3/300s, forget-password 2/300s, reset 3/300s, demo-session 10/60s) keys on the client-supplied X-Forwarded-For header. The ALB does not overwrite it, so rotating the header resets the counter — the limits are the only brute-force control on sign-in, and they are client-controlled.

Reproduction.

$ for i in 1 2 3 4 5; do
    curl -s -o /dev/null -w "%{http_code}\n" -X POST \
      https://api.staging.peliqan.eu/api/auth/sign-in/email \
      -H 'Content-Type: application/json' \
      -d '{"email":"rt-tester1@example.com","password":"wrongpass1"}'
  done
401
401
401
429
429

$ curl -s -o /dev/null -w "%{http_code}\n" -X POST \
    https://api.staging.peliqan.eu/api/auth/sign-in/email \
    -H 'X-Forwarded-For: 10.66.0.1' \
    -H 'Content-Type: application/json' \
    -d '{"email":"rt-tester1@example.com","password":"wrongpass1"}'
401        # counter reset — brute force resumes immediately

Impact. Unlimited online password brute force against any account, user-creation spam, demo-session spam. The generic sign-in error (Invalid email or password) prevents enumeration, but the timing cap is gone.

Recommendation. Derive the client IP server-side (first untrusted hop) or overwrite X-Forwarded-For at the ALB before the app keys limits on it; consider a global (per-account) floor for sign-in.

F2 Unauthenticated self-registration mints a real investor account HIGH

Summary. POST /api/auth/sign-up/email is open unauthenticated and creates a fully functional account (role USER, performWrites: true) with an immediate session cookie (Max-Age=604800). The new user can upload documents (S3 write), create/patch positions, create liquidity interests, archive documents, and delete document files — an unauthenticated write path into staging data.

$ curl -i -X POST https://api.staging.peliqan.eu/api/auth/sign-up/email \
    -H 'Content-Type: application/json' \
    -d '{"name":"RT Tester","email":"rt-tester1@example.com","password":"Rt-Pass-12345!"}'
HTTP/2 200
set-cookie: __Secure-better-auth.session_token=…; Max-Age=604800; HttpOnly; Secure; SameSite=Lax
{ "token":"UCCob2nw…", "user":{ "id":"zMCbWj20…", "email":"rt-tester1@example.com", … } }

Guardrails observed. demo.peliqan.eu addresses are reserved (400 "Emails on demo.peliqan.eu are reserved", case-insensitive). Sign-up is rate-limited 3/300s per IP — bypassable per F1.

Impact. Unauthenticated writes, tenant pollution, and it enabled the cross-tenant (IDOR) testing in this report. Confirm whether open sign-up is intended for staging; if not, gate it.

F3 Impersonation token in URL; unauthenticated exchange with no origin check MEDIUM / HIGH*

Summary. The admin impersonation flow mints a 60-second single-use token and redirects to /auth/impersonate?token=<uuid> on the app (and admin) hosts. The page (200 SSR, renders without a session) auto-POSTs the token, unauthenticated, to POST /api/impersonation/exchange-impersonation-token, which sets the signed session cookie of the impersonated user.

  • Live token in the URL → exposed via browser history, Referer, proxy logs, analytics (Sentry is instrumented in the bundles).
  • No origin check on the exchange: Origin: evil / null / absent all processed identically → a leaked token is also a cross-site CSRF primitive (set-auth-token is exposed for credentialed reads).
  • Error oracle: 404 invalid · 410 expired · 400 validation (UI text differs for 410 vs other).
# bad token, arbitrary origin — processed, not origin-rejected:
$ curl -i -X POST https://api.staging.peliqan.eu/api/impersonation/exchange-impersonation-token \
    -H 'Origin: https://evil.example.com' -H 'Content-Type: application/json' \
    -d '{"token":"6f1e2c9d-3a4b-4c5d-8e9f-0a1b2c3d4e5f"}'
HTTP/2 404
{"error":"not_found","message":"Invalid token"}

Browser-CSRF nuance. The endpoint accepts only Content-Type: application/json (text/plain/urlencoded bodies parse empty), so a cross-site JS request from an untrusted origin is blocked by the CORS preflight (no ACAO reflection). The missing server-side origin check therefore matters for trusted-origin contexts (compromised app/admin/marketing page, subdomain takeover, XSS on a trusted origin) and for non-browser clients — a defense-in-depth gap, not a standalone cross-site trigger.

Impact. Any leak of a live token within its 60 s window yields an authenticated session of the impersonated (possibly admin) user. Replay is single-use; expiry/replay semantics confirmed in code/UI, not externally demonstrable without an admin-minted token.

Recommendation. Move the token out of the URL (POST-only handoff / one-time code), verify Origin on the exchange, and short-token logging of exchanges.

F4 demo/session CSRF — session cookie overwritten from any origin MEDIUM

Summary. The demo-session mint (intended for the marketing embed) performs no origin check: any site can cross-origin POST it and the response Set-Cookies the shared DEMO session onto api.staging.peliqan.eu. A cross-site fetch need not read the response — the victim's existing API session cookie is replaced with the shared demo session (SameSite=Lax does not protect a cookie that is set, not sent).

$ curl -i -X POST https://api.staging.peliqan.eu/api/auth/demo/session \
    -H 'Origin: https://evil.example.com' -H 'Content-Type: application/json' \
    -d '{"email":"investor@demo.peliqan.eu"}'
HTTP/2 200
access-control-allow-credentials: true
set-cookie: __Secure-better-auth.session_token=4no5rh…; HttpOnly; Secure; SameSite=Lax
{"ok":true}

Browser-CSRF nuance. As in F3, the JSON-only content type means the preflight gates untrusted origins; the effect is real for trusted-origin contexts and non-browser clients, and it is the mechanism the intended marketing embed relies on (note: the embed's own origin is not reflected in ACAO — verify the embed actually works via app.staging).

Impact. Low-privilege downgrade: victim is switched to the shared read-only demo identity (API session displaced; the victim now views all visitors' shared demo state). Rate-limited 10/60s (bypassable per F1).

Recommendation. Enforce BETTER_AUTH_TRUSTED_ORIGINS on the mint, or require a short-lived nonce issued by the embed page.

F7 Document upload quirks LOW

  • MIME by declaration only — allowlist (pdf/png/jpeg/tiff/webp/heic/heif, else 415) checks the client-declared type; content is not sniffed. A PDF declared as image/png is accepted (MIME confusion; the doc-AI pipeline then treats bytes as image).
  • Filename → storageKey: traversal names accepted verbatim in fileName (../../../../../tmp/../../evil-traversal.pdf → 201) but sanitized in the S3 key (_.._.._.._.._tmp_.._.._evil-traversal.pdf) — no escape from the document-files/{docId}/{uuid}/ prefix.
  • Size cap: 10 MiB accepted, 50 MiB rejected — 413 {"error":"payload_too_large","message":"File exceeds 52428800 bytes"} (exact limit disclosed). A 10 MiB all-zero PDF is accepted and the doc-AI pipeline marks the document FAILED (graceful).
  • Presigned URLs: bucket peliqan-storage-staging, per-object key, STS token (ASIA…), X-Amz-Expires=300.
  • DELETE /api/document-files/{id} works for the owner even on classified files (204) — the flagged "500 on scanned files (audit FK RESTRICT)" bug did not reproduce from this foothold.
  • POST /api/portfolio/documents/{id}/archive|unarchive — real write routes; owner-scoped (cross-owner → 404), write-gated for demo (403 demo_mode).

F8 Validation-error information disclosure INFO

Unauthenticated 400s leak schema details: role enum USER|ADMIN|DEMO, liquidity types SELL|NAV_LOAN, required-field lists, Zod paths. Useful targeting data, low direct impact. Consider a generic validation message in non-dev environments.

F9 Filename >255 chars wedges the document list (availability) MEDIUM

Summary. Upload accepts 10 KB filenames (F7). The doc-AI pipeline defaults the document title to the filename; the API's response schema validates title ≤ 255 chars. From that point every serialization of the row fails:

$ curl -b user2 https://api.staging.peliqan.eu/api/portfolio/documents
HTTP/2 400
{"error":"validation_failed","message":"Invalid input",
 "fields":{"data.4.title":[{"rule":"too_big","message":"Too big: expected string to have <=255 characters"}]}}

$ curl -b user2 https://api.staging.peliqan.eu/api/users/{user2}/portfolio/documents   # admin/portfolio view route
HTTP/2 400   (same)

$ curl -b user2 https://api.staging.peliqan.eu/api/portfolio/documents/{long-title-doc}
HTTP/2 400   (single fetch also fails — the row is unreadable)

Recovery. POST /api/portfolio/documents/{id}/archive performs the write (archivedAt is set) but its response also 400s; after archiving, the default list (active docs) returns 200 again. No user-facing route deletes or renames a document, so the row stays wedged in the archive (admin archive view uses the same serialization).

Impact. Any real user can, with a single upload of a long-named file (common from mail/Slack), break the document views for their own portfolio and the admin's views of that document — a read-path availability bug triggered by a normal client-supplied string. The write-gate is unaffected (demo cannot upload), but this is a demo→write-adjacent surface: the doc-AI pipeline's title derivation should be truncated/clamped at ingest.

Recommendation. Clamp title at 255 chars on upload/classification (or reject filenames >255), and validate request fields against response schemas.

F10 Unauthenticated 500 on the impersonation exchange (empty body) INFO

$ curl -i -X POST https://api.staging.peliqan.eu/api/impersonation/exchange-impersonation-token \
    -H 'Content-Type: application/json'        # no body
HTTP/2 500
{"error":"internal","message":"Internal server error"}

With Content-Type: application/json but no body, req.body is undefined and the route destructures it before validation → 500 (any query value, with or without ?token=). Without the header the framework defaults the body to {} → clean 400 Zod. Not exploitable (generic message, no data leaked), but it shows the security-critical route lacks the body-type pre-validation the better-auth endpoints have (all of which return 400 in the same case) — fix by parsing the body through Zod first.

Open Items / Follow-Up

  • SSRF via document content — tested, no signal. Uploaded three PDFs (control; link-annotation + text URL to http://169.254.169.254/latest/meta-data/; link-annotation + text URL to http://rt-ssrf-abc123.invalid/). All classified within ~3–6 min with identical timing, no lastError, type OTHER — the pipeline appears fully local. A collector-based re-test would be needed to rule out rare fetch paths.
  • XXE in allowed non-PDF types (heic/tiff): JPEG XMP attempted (decode failure masked it); HEIC XMP not crafted.
  • Impersonation-token replay & 60 s expiry end-to-end (requires an admin-minted token).
  • Delete-DocumentFile 500 (audit FK RESTRICT): all owner deletes returned 204 (incl. classified files) — likely needs an admin-reviewed file state; not reproducible without admin.

Top Recommendations

  1. Normalize client IP at the ALB (overwrite/ignore client X-Forwarded-For) for all rate limiting (F1).
  2. Gate or confirm intent of open self-registration on staging (F2); add email verification before write access if open.
  3. Keep the impersonation token out of the URL and verify origin on the exchange (F3).
  4. Apply the trusted-origins check to demo/session or issue a per-embed nonce (F4).
  5. Gate generate-schema and /api/system/health behind auth or dev-only flags (F5/F6).
  6. Clamp document titles/filenames at 255 chars on ingest so one upload can't wedge the list (F9); sniff content vs declared MIME (F7).
